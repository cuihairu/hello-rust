# impl Trait

`impl Trait` writes "some type that implements a certain trait" directly into a signature: in argument position it is syntactic sugar for generics, and in return position it is an **opaque type** — the caller knows the capabilities but not the concrete type. This page covers the semantic difference between the two positions, the standard way to return closures, and the lifetime-capture rules that are easiest to trip over.

## Argument position: syntactic sugar for generic parameters

`fn f(x: impl Debug)` expands to `fn f<T: Debug>(x: T)`; each call is monomorphized on the argument's type, at zero cost:

```rust
use std::fmt::Debug;

// APIT：参数位置的 impl Trait 是泛型参数的语法糖
fn show_apit(x: impl Debug) {
    println!("{x:?}");
}

// 等价的泛型写法
fn show_generic<T: Debug>(x: T) {
    println!("{x:?}");
}

fn main() {
    show_apit(42);
    show_generic(42);
    show_apit("hello");
    show_generic("hello");
}
```

Actual run output:

```text
42
42
"hello"
"hello"
```

Generic parameters are more expressive: when two arguments must be the same type (`fn max<T: Ord>(a: T, b: T)`), or when a bound needs to go into a `where` clause, you still have to use the generic form.

## Return position: hiding the concrete type

Return-position `impl Trait` (RPIT) has completely different semantics: it is a single **fixed but hidden** concrete type, and all return paths must be that one type. Want to return one of two iterators depending on a condition? The compiler won't accept it — the hidden type must be unique:

```rust
fn pick(flag: bool) -> impl Iterator<Item = i32> {
    if flag {
        vec![1].into_iter()   // Vec<i32>::IntoIter
    } else {
        0..3                  // Range<i32>
    }
}

fn main() {
    for x in pick(true) { println!("{x}"); }
}
```

Actual run output (excerpt, the compiler suggestion omitted):

```text
error[E0308]: `if` and `else` have incompatible types
 --> pick.rs:5:9
  |
2 | /     if flag {
3 | |         vec![1].into_iter()   // Vec<i32>::IntoIter
  | |         ------------------- expected because of this
4 | |     } else {
5 | |         0..3                  // Range<i32>
  | |         ^^^^ expected `IntoIter<{integer}>`, found `Range<{integer}>`
6 | |     }
  | |_____- `if` and `else` have incompatible types
  |
  = note: expected struct `std::vec::IntoIter<{integer}>`
             found struct `std::ops::Range<{integer}>`
help: you could change the return type to be a boxed trait object
  |
1 - fn pick(flag: bool) -> impl Iterator<Item = i32> {
1 + fn pick(flag: bool) -> Box<dyn Iterator<Item = i32>> {
```

The suggestion in the error is exactly the way out: when the type genuinely has to switch at runtime, use `Box<dyn Trait>`, at the cost of a heap allocation plus dynamic dispatch (see [Trait objects](./trait-objects)).

### Returning closures

A closure's type is an anonymous type generated by the compiler, and **you cannot write its name** in a signature — RPIT happens to need no name, which makes it the standard way to return closures:

```rust
// 返回闭包：impl Trait 零成本，Box<dyn Fn> 灵活（可存进同一集合）；
// 注意每个闭包都要 move，否则它借用局部 x，函数返回后 x 已销毁
fn make_adder(x: i32) -> impl Fn(i32) -> i32 {
    move |y| y + x
}

fn make_adder_boxed(x: i32) -> Box<dyn Fn(i32) -> i32> {
    Box::new(move |y| y + x)
}

fn main() {
    println!("impl Trait: {}", make_adder(5)(10));
    println!("Box<dyn>:   {}", make_adder_boxed(7)(10));
}
```

Actual run output:

```text
impl Trait: 15
Box<dyn>:   17
```

What happens without `move` — the closure borrows the local variable `x`, but `x` is destroyed when the function returns:

```rust
fn make_adder(x: i32) -> impl Fn(i32) -> i32 {
    |y| y + x   // 不 move：闭包借用 x，但 x 在函数返回时被销毁
}

fn main() {}
```

Actual run output (excerpt, the compiler suggestion omitted):

```text
error[E0373]: closure may outlive the current function, but it borrows `x`, which is owned by the current function
 --> adder.rs:2:5
  |
2 |     |y| y + x   // 不 move：闭包借用 x，但 x 在函数返回时被销毁
  |     ^^^     - `x` is borrowed here
  |     |
  |     may outlive borrowed value `x`
help: to force the closure to take ownership of `x` (and any other referenced variables), use the `move` keyword
  |
2 |     move |y| y + x   // 不 move：闭包借用 x，但 x 在函数返回时被销毁
  |     ++++
```

## Lifetime-capture rules

The type hidden by an RPIT may **borrow** from the input parameters. Edition 2021 captures only the lifetimes that appear in the `impl Trait` bounds; when the hidden type additionally captures a lifetime not in the bounds, you must declare it explicitly:

```rust
fn len_of(x: &str) -> impl Fn() -> usize {
    move || x.len()
}

fn main() {
    let s = String::from("hello");
    let f = len_of(&s);
    println!("len = {}", f());
}
```

Actual run output (excerpt, the compiler suggestion omitted):

```text
error[E0700]: hidden type for `impl Fn() -> usize` captures lifetime that does not appear in bounds
 --> len_of.rs:3:5
  |
2 | fn len_of(x: &str) -> impl Fn() -> usize {
  |              ----     ------------------ opaque type defined here
  |              |
  |              hidden type `{closure@len_of.rs:3:5: 3:12}` captures the anonymous lifetime defined here
3 |     move || x.len()
  |     ^^^^^^^^^^^^^^^
```

Follow the hint and add `use<'_>` (precise capturing), declaring the anonymous lifetime as captured:

```rust
fn len_of(x: &str) -> impl Fn() -> usize + use<'_> {
    move || x.len()
}

fn main() {
    let s = String::from("hello");
    let f = len_of(&s);
    println!("len = {}", f());
}
```

Actual run output:

```text
len = 5
```

Starting with edition 2024 this rule is relaxed: an RPIT by default captures **all** lifetimes in scope, so the first version compiles even without `use<'_>` (verified locally under rustc 1.99.0, edition 2024). Signatures like `-> impl Iterator<Item = &str>` are fine under both editions — that lifetime appears in the bounds, so it was already captured in 2021.
